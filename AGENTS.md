# Working with this repository

- When I ask to plan or discuss, keep it brief and conversational. Ask what the musician puts in and what they should see or hear. Wait for my go-ahead before implementing.
- When I ask a question only, answer it without editing code. If I ask you to restate a plan and wait for permission, do that first.
- Commit completed changes and push them after each implementation or documentation turn. Stage the files or hunks for that task so unrelated local edits stay available to their author.
- You may run PowerShell commands within the scope of my request without asking me for confirmation.

## Coding conventions

- In HTML, start each element on a new line. A `<span>` may stay inline with the surrounding text.
- Indent each child one level beneath its parent using a tab. Use four spaces per indentation level in Python.
- Define functions outside other functions. An inner function used to implement a Python decorator is the exception.
- Give functions longer than three lines of code a brief docstring or documentation comment appropriate to the language.
- Format CSS in readable blocks with one declaration per line.

## Interface and musical notation

- Use uppercase interface labels and uppercase Roman numerals. Put MAJ or MIN in the chord name only.
- Use the inversion figures ROOT, 6, 6 4, 7, 6 5, 4 3, and 2.
- Keep Saved Projects as the first standalone navbar link. Group tools under Music Composition or Math Music Experiments.
- Keep composition tools simple and useful for exporting ideas to other music software. See [the handover](HANDOVER.md) for the musical and playback decisions already implemented.
